# Google 고객 계정과 기존 여행 기록 연결

## 고객 동선

- 신규 고객: Google 로그인 → 맞춤 견적 요청 → 로그인한 계정에 접수 이력이 저장된다.
- 기존 고객: 카카오톡·이메일의 기존 링크 → Google 로그인 → 기존 기록에 등록된 이메일 또는 휴대폰으로 인증번호 수신 → 해당 기록 연결 → 원래 문서로 복귀한다.
- 마이페이지의 **기존 견적 연결**에서도 받은 링크를 붙여 넣을 수 있다. 연결된 기존 견적과 신규 견적은 같은 목록에서 확인한다.
- Google 계정 이메일과 기존 견적 연락처가 달라도 기존 연락처로 인증할 수 있다. 기록별 최초 연결 후에는 같은 계정의 유효한 로그인 세션으로 열 수 있다. 로그아웃·세션 만료 시에는 다시 로그인한다.
- 기존 연락처를 사용할 수 없거나 다른 계정에 연결된 기록은 자동 연결하지 않는다. 담당자가 별도로 본인을 확인해 복구해야 한다. 연락처·이름 일치로 여러 기록을 일괄 연결하지 않는다.

## 서버 권한

`request`는 INHASU `requests`, `quote`는 이전 사이트 `quotes`, `reservation`은 상품·수동 `reservations`이다. 출처가 다른 같은 ID를 섞지 않는다.

- `requests` 소유권은 `customer_resource_links(source, resource_id, user_id)`에만 저장한다. 예전 공개 API에 임의로 넣을 수 있었던 `data.userId` 등은 신뢰하지 않는다.
- `quotes`·`reservations`는 기존 `user_id`를 정본으로 사용한다. 미연결 기록 인증 후 소유자를 원자적으로 설정한다. 이미 다른 소유자가 있으면 변경하지 않는다.
- 고객 토큰·UUID는 기록을 찾기 위한 값이다. 개인정보 조회, 여행자 저장, 서명, 입금 신고, 계약·일정표 조회 등은 로그인과 소유권을 별도로 검사한다.
- 신규 견적은 고객 폼 필드만 받는다. 고객이 보낸 계약·입금·견적 발행 상태는 저장하지 않는다. 항공권 등 비공개 첨부 업로드도 로그인한 고객 또는 실제 관리자만 사용할 수 있으며, 비공개 파일 다운로드는 기존 관리자 전용 권한을 유지한다.
- 관리자 미리보기는 검증된 관리자 세션 또는 해당 레거시 API의 실제 관리자 인증을 사용한다. URL의 `adminId`, `preview`, `guide`만으로 권한을 부여하지 않는다.
- 기존 모바일 관리자 편집기 미리보기는 `POST /api/auth/legacy-admin/check`에서 공유 토큰을 검증한다. 새 세션·자격증명을 발급하지 않으며 확인한 토큰은 허용된 동일 출처 고객 API에만 보낸다. 명시 로그아웃·일반 고객 로그인에서는 이전 관리자 토큰도 정리한다.
- Google OAuth는 정상 응답의 `email_verified=true`와 Google `sub`를 검사한다. 이메일만 같은 이전 사용자 계정에 자동 로그인시키지 않는다. Google 연결이 없는 기존 `users` 계정과 이메일이 충돌하면 담당자의 계정 복구가 필요하다.

## 인증번호

`GET /api/customer-access/status`, `POST /challenge`, `POST /verify`, `GET /history`를 사용한다. 클라이언트가 수신 주소나 소유자 ID를 지정할 수 없다. 인증 전에는 마스킹된 연락처만 제공한다.

- Web Crypto로 만든 8자리 숫자, 10분 유효, 최대 5회 시도, 발급한 로그인 계정에 종속, 1회만 사용.
- DB에는 원문 인증번호를 저장하지 않는다. 서버 비밀키로 만든 HMAC을 저장하고 비교한다.
- 재발송 간격 60초, 기록별 시간당 5회, 계정별 시간당 10회, IP별 시간당 30회로 제한한다. 서버 인스턴스가 달라도 D1에서 제한한다.
- 실제 발송 접수 결과를 확인한 뒤에만 인증번호를 활성화한다. SMS의 HTTP 200 내부 오류도 실패로 처리한다.
- 최종 소유권 저장 트랜잭션에서 소유자·연락처·기존 토큰 변경을 다시 검사한다. 발급 이후 연락처가 바뀐 인증번호로 연결할 수 없다.
- 고객 API는 `no-store`, 사이트 밖 Origin의 쓰기 요청은 거절한다.

## 배포 설정과 기존 데이터

새 Cloudflare 바인딩은 필요 없다. D1 표 3개는 사이트 스키마 버전 6에서 추가되며 기존 `requests` 칸과 고객 링크를 변경하지 않는다. 별도 대량 소유권 마이그레이션은 하지 않는다.

필요한 서버 환경변수:

| 용도 | 설정 |
| --- | --- |
| Google 로그인 | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, 실제 도메인의 OAuth 콜백 URL |
| 인증번호 HMAC | 선택적으로 `CUSTOMER_LINK_SECRET`; 없으면 `GOOGLE_CLIENT_SECRET`을 용도 분리하여 사용 |
| 이메일 인증 | `RESEND_API_KEY`, 기존 `MAIL_FROM` 발신 도메인 설정 |
| 휴대폰 인증 | `SOLAPI_API_KEY`, `SOLAPI_API_SECRET`, 등록된 `SOLAPI_SENDER` |

인증번호 휴대폰 발송은 고객이 직접 선택한 SMS이며 카카오 알림톡 대체 발송이 아니다. 카카오 템플릿과 자동 발송 규칙은 이 작업에서 바꾸지 않는다. 발송 제공자가 준비되지 않은 채널은 고객에게 선택지로 표시하지 않는다.

연락처가 없는 기록, 기존 계정 이메일 충돌, 다른 계정에 이미 연결된 기록을 운영자가 복구할 때는 별도 본인 확인을 거친다. 화면의 이름이나 전화번호만 보고 D1 소유자를 수정하지 않는다.

## 검증

`npm test`, `npx tsc --noEmit -p tsconfig.app.json`, `npm run build`. 인증·연결 회귀 테스트는 실제 Hono·Lucia·메모리 SQLite를 사용하고 Google·Resend·Solapi 외부 요청은 모두 모의 응답으로 차단한다. 운영 데이터 수정이나 실제 고객 인증번호 발송 없이 검증한다.

로컬 Wrangler 4.67.0 / Windows / Node 24에서 Functions 번들 생성 성공 메시지와 `index.js` 생성 후 프로세스가 `0xC0000409`로 종료되는 현상을 확인했다. 생성된 번들은 `node --check`를 통과했다. 따라서 이 검증을 운영 Workers 실행·배포 성공으로 해석하면 안 된다. 배포 전 배포 환경에서 Functions 빌드와 실제 Google OAuth 복귀·선택한 발송 제공자의 인증번호 수신을 확인해야 한다.
